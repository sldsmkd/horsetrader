# Eclipse 3 — The Public Interface

_What a client needs to drive the economic model, stated as a boundary. The
settled model is 2.DESIGN.md; this is the surface it presents outward. The web
app is one client; a CLI report is another (OVERVIEW goal: the whole model runs
headless). Anything below depends only on the bake and account state — no DOM,
no presentation. Frontend-pure: consume the bake as-is._

## The cut

The loop is `shields write account state → streams read it into events → the
fold reads events into money → surfaces read both`. The **public interface is
the seam between the engine and its clients** — it falls across that loop in one
place:

```
        CLIENT (web app, CLI, …)                ENGINE (headless core/)
  ┌───────────────────────────────┐      ┌──────────────────────────────────┐
  │  shields  ──write──────────────┼─────▶│  account state (the write store) │
  │  surfaces ──read───────────────┼──┐   │  streams → settled world         │
  │  (cards, lane, balance line,   │  │   │  fold → P_income → P_final       │
  │   tooltip, minimap, formatter) │  └──◀─┼── settled world + P_final + q\
  │                                 │      │  reconcile(commitments)         │
  └───────────────────────────────┘      └──────────────────────────────────┘
```

The engine is **one object a client holds** (the coordinator). It exposes four
verbs and a handful of value types. Everything the client does is: construct it,
write account state, read derivations, observe recomputes. Presentation never
crosses leftward; the bake and DOM never cross rightward.

## Construction — what you build it with

Two kinds of input, by lifetime:

- **The bake** (immutable, load-once): the events bundle, the config tables
  (`reward_structures`/`reward_maps`/`gacha`), and the clock/zone the
  day-bucketed core is read in (`now`, `timeZone`). Pure game data; the client
  passes it straight from the bake, never authors a value in it.
- **The account-state store** (mutable, persisted): where the user's writes
  land. Defaults to localStorage; an in-memory store makes the engine testable
  and lets a CLI run against a fixture.

```ts
createCoordinator({
  bundle, config, gacha,        // the bake — frozen game data
  now, timeZone,                // the clock — day-bucket ingress
  store?,                       // account-state persistence (defaults localStorage)
  streams?,                     // the registry; defaults to the full set, injectable for tests
}): Coordinator
```

The `streams` registry is the one declaration shape from 2.DESIGN — a list of
`Stream = id + enabled(ctx) + claims + events(ctx)`. It is a **construction
input, not a runtime surface**: a client swaps it only to test. Its partition is
asserted at construction (disjoint claims), so an ill-formed registry fails to
build, not to fold.

## Value types that cross the boundary

Four shapes, and only four, travel between client and engine.

**`ResourceVector`** — a keyed, signed integer vector (`free_carats`,
`paid_carats`, `trainee_tickets`, …). The reward keys *are* the resource
dimensions; per-dimension arithmetic, no scalar, signed and allowed negative.
The one currency the whole interface speaks in.

**The settled-world `Event`** — the render source (below). The baked event
record, **its reward face resolved and a `visible` flag** — a superset of the
bake, nothing dropped:

```ts
interface Event {            // = the baked record, plus:
  key: string;               // stable key — and the emission `source` (one naming system)
  type: string;              // trainee | support | cm | story | anniversary | holiday | …
  start: CalendarDate;       // bucketed once, at ingress
  end:   CalendarDate;
  rewards: ResourceVector;   // the RESOLVED face — what the card shows, stamped by the owning stream
  visible: boolean;          // false ⇒ ledger-only (synthesised cadence); off the lane
  …                          // name, art, every other baked display field rides along untouched
}
```

The face is **resolved by the engine** (the `GradedStamp` row, the CM rank
payout, the story era×tier lookup) so the client never re-derives a reward
amount. This is the interface's load-bearing change — see below.

**The `Projection`** — `{ ledger, series }`. The `ledger` is the rich attributed
fact list (`(date, stream, source, resource, amount)`) for the tooltip and
per-stream what-ifs; the `series` is the dense O(1) balance cache
(`balanceAt(date)`, plus `dates` change-points and `extent`). The client reads
**P_final** here — income with the reconciliation tail folded in. P_income is
internal machinery, surfaced only through the `availableFor` query.

**Account-state sections** — the write store, by class:
- _fold inputs_ (change the money): `snapshot`, `config` (carrying play +
  identity + subscriptions), `commitments`, `rushed`.
- _view-only_ (no money effect): `favourites`.
- _ephemeral_ (never persisted): per-stream dev toggles.

## Write — typed intent over one path

```ts
commit(eventKey: string, pity: number): void   // raise/adjust a claim (0 clears it)
setPlay(…): void                               // play-style sliders
setIdentity(…): void                           // club rank, trainer identity
setSubscriptions(…): void                      // daily pack date, training pass
saveSnapshot(…): void                          // the dated base reading
setRushed(eventKey: string, on: boolean): void // discrete payout to start
setFavourite(id: string, on: boolean): void    // view-only; no money effect
setEnabled(stream: string, on: boolean): void  // ephemeral dev toggle
```

The public writes are **typed mutators** — each names the user intent a shield
commits (clarity of intent outward). Inward they are all sugar over **one
private write path**: patch an account-state section, persist, re-derive,
notify. The design's "commit pity ≡ change a slider — same operation" survives
as the *implementation* invariant, not the API shape; no mutator can do
anything the one path can't. The projection is never written, only derived: a
write mutates account state, the engine re-runs the pure fold over `(bake,
account state)`, then fires `subscribe`. Nothing is reversed because nothing
was written — re-derivability, not reversibility. A commitment is a stored
*claim* (`commitments[key] = pity`), read fresh by every fold; the referent
event never knows.

`setEnabled` is the dev/debug isolation toggle — it drops a stream from the next
fold but is **never** persisted into account state. Whole-stream gating is sound
by the linear fold (removing a summand can't perturb the others).

## Read — the settled world, the balance, the query

```ts
settledEvents(): readonly Event[]               // the settled world — the render source
projection(): Projection                        // P_final: ledger + balance series
balanceAt(date: CalendarDate): ResourceVector   // convenience O(1) into the P_final series
availableFor(eventKey: string): ResourceVector | undefined  // pre-claim resources at an event
document(): AccountState                         // the persisted account state (read-only)
streams(): { id: string; enabled: boolean }[]   // dev-toggle state
recovered(): boolean                             // stored state was unreadable, started clean
```

**The settled world is the render source.** This is the one place the interface
*changes* what the client does today. Currently the UI reads `bundle.events`
directly and re-derives reward faces itself (the card's own era×tier lookup, the
CM stamp). Under the settled model, `settledEvents()` returns the union of all
stream outputs with faces already stamped and `visible` set; **cards =
`settledEvents()` where `visible`**, reward faces included. "What am I
rendering?" is answered by construction — the same value that feeds the fold
feeds the lane. The client stops joining back to the bundle for reward amounts;
it renders straight off the event. Synthesised cadence events (routine dailies,
minted keys, `visible:false`) are on the ledger but filtered off the lane by
their own flag. The name carries the *stage*: three layers share the noun
(`bundle.events` raw, `Stream.events(ctx)` per-stream, this union), and the
raw-vs-settled distinction is exactly the bug class the rename prevents — a
client grabbing `bundle.events` out of habit and re-deriving a face.

**The balance the user sees is P_final** — income with debits folded in.
`projection().series` / `balanceAt` is the minimap line, the cursor balance, the
scrub cache. It never re-folds on scrub.

**`availableFor` is a query against P_income, not a series read.** It answers
"what would a claim against this event see?" — income at the event's `end` minus
every earlier-by-start claim, self-excluding by construction. The shield and the
above-lane card read it for committed events; `undefined` when uncommitted (fall
back to `balanceAt(end)`). It re-runs the pure ordered reconciliation on demand,
legitimised by the single-threaded write path: every read is against a settled
world. It must hit **P_income, not the flattened P_final** — a self-excluded
final read would wrongly deduct overlapping later-starting claims. (Renamed from
today's `bannerAvailable`: claims generalised off banners — any event can carry
one — so the prefix read as a type constraint that no longer exists.)

**Attribution joins on one key.** A ledger entry's `source` is the event's
stable key; `settledEvents()` keys events by the same string. Tooltip
provenance, per-stream toggles, and "this banner cost you X" all join
`ledger.source → settledEvents().key` with no parallel vocabulary. A debit's `source` is *the claimed
event's* key (`banner-kita` cost you X) — income-vs-spend is which projection you
read, never a string on the row.

## Observe

```ts
subscribe(listener: () => void): () => void
```

Fired once after each recompute (any mutator, including `setEnabled`); returns
an unsubscribe. **Reads never notify** — scrubbing `balanceAt`, hovering the
tooltip, reading `settledEvents()` are broadcast-free, so the cheap query path
stays off the recompute seam. A bare callback keeps the engine DOM-agnostic; the client
owns "re-render on notify".

## What does NOT cross the boundary

The line is _account fact_ vs _presentation_ (`projection-is-account-not-view`):

- **No DOM, no rendering.** The engine returns values; the client paints them.
- **No formatting.** The engine holds `-50`; sign, resource label, grouping,
  carat icons are one formatter in the client. (The old `+-50` bug was a client
  concern leaking nowhere near here.)
- **No axis / zoom / timezone-as-view / theme.** Day-bucketing the core needs a
  zone (ingress), but *which* span is on screen, pixels-per-day, the cursor
  position — all client. One ledger, many views; the engine ships the ledger.
- **No clamping or affordability enforcement.** Negative free carats are valid,
  communicative output. The engine never floors a balance; the planner informs,
  the client decides how to show a deficit.
- **No reward-amount authorship.** Every number is baked. A game-data literal on
  the client side of this line is a smell.

## Decisions (RESOLVED 2026-06-12)

- **`settledEvents()` granularity — flat.** One `Event[]` decorated with
  `visible`; the lane's filter is trivial and the lane is the only consumer of
  the flag. No pre-split `{ visible, ledgerOnly }` convenience.
- **P_income stays internal** — YAGNI. `availableFor` is its only window. If a
  client ever legitimately needs the raw pre-reconciliation series (a CLI
  "income before commitments" report, say), that's a second read method then,
  never a leak into `projection()`.
- **Typed mutators are the public write surface** — clarity of intent outward
  (`commit`, `setPlay`, `saveSnapshot`, …), one private patch-persist-derive-
  notify path inward. "Commit pity ≡ change a slider" is the implementation
  invariant, not the API shape.
- **Naming.** `settledEvents()` — carries the stage, disambiguating the three
  layers of the noun (raw `bundle.events` / per-stream `Stream.events(ctx)` /
  this union); `world` rejected (game-map connotations), `timeline` rejected
  (it's literally the UI lane component, `ui/views/timeline.ts` — the wrong
  side of the boundary). `availableFor(eventKey)` — reads as the question it
  answers; `bannerAvailable` rejected (the prefix read as a type constraint
  the generalised-claims model no longer has).
